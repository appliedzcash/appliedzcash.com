Wishlist

Signature login

A wallet signs a login message with a wallet key. The app examines the signature. The login is off the chain: it has zero transactions and zero fees.

Most wallets do not have this function today. This page has three designs. The viewing key signature is from Julian (craftsoldier). The app key signature is from c-node. The identity key signature is from hitch (hitchho), in the zafu wallet. zafu has a form of it today.

Problem

An app uses Log in with Zcash with the wallets of today. Each login is two payments. Thus, each login has two transactions, two fees and a delay. The service also needs a worker with a code key.

With a signature, these costs are zero. On Ethereum, apps use ERC-4361 for this function. On Zcash, wallets sign messages with transparent keys at most. ZIP 304 is for Sapling keys only.

Mechanism

Viewing key signature

Each shielded receiver of an address is already a public key. Its secret key is the incoming viewing key ivk. 

pk_d = [ivk]g_d

g_d   the base point of the receiver, from its diversifier
pk_d  the public key in the receiver

The wallet makes a Schnorr signature with ivk as the secret key and g_d as the base point. The app has g_d and pk_d from the address, and it examines the signature with them. Thus, the address is the account of the user, as in Log in with Zcash.

The wallet calculates g_d from its own diversifier only. An app that chooses the base point B can find [ivk]B from the signature. If B is the epk of an Orchard note to the user, [ivk]B is its shared secret. For a Sapling note, the shared secret is [8ivk]B. Thus, the app can read that note if the wallet uses its epk as the base point.

The signature contains a point R and a number. The challenge is a hash of a domain tag, the diversifier d, pk_d, R and the login message. Thus, the signature is valid for one receiver and one login message only.

App key signature

A shielded wallet has a spend authorizing key ask and its public key ak. In RedDSA, a wallet can randomize this key pair with a secret number α. Each shielded spend already has a signature from a randomized key. 

α   = PRF(wallet secret, domain)
rk  = ak + [α]G
rsk = ask + α

domain  the domain of the app, for example app.example
G       the base point of the spend signatures
rk      the public key of the user at this app
rsk     the secret key of the user at this app

The wallet calculates α with a keyed hash, from a secret of the wallet and the domain of the app. Thus, the wallet has a different key pair for each app. The wallet calculates the secret from the seed, with ZIP 32 registered key derivation. If the secret is from the full viewing key, each holder of that key can calculate α. Thus, each holder of the full viewing key can link the app keys of the user.

A wallet that the user restores from the seed calculates the same keys again. An account that participants make with a FROST distributed key generation has no seed. For that account, developers must give the source of the secret in the spec.

Identity key signature

The wallet calculates a set of identity keys from the seed phrase. These keys are for logins and messages only. In site mode, the wallet uses a different Ed25519 key pair for each app. Site mode is the default. The zafu wallet has this design, with the name zid. 

m     = SHA-256(seed phrase)
root  = HKDF-SHA256(m, salt "zafu-zid-v2", info "identity-root", 64 bytes)
id    = HMAC-SHA512(root, "identity:default")
id_sk = the first 32 bytes of HMAC-SHA512(id, "site:" + origin)
id_pk = the Ed25519 public key of id_sk

origin  the origin of the app, for example https://app.example
id_sk   the secret key of the user at this app
id_pk   the public key of the user at this app

The input of SHA-256 is the seed phrase as UTF-8 bytes. The phrase is lowercase English words with one space between them. zafu does not use the NFKD normalization of BIP 39. The wallet calculates the Zcash keys from the BIP 39 seed, a PBKDF2 hash of the seed phrase. The identity keys are from a different hash of the seed phrase. Thus, the identity keys and the Zcash keys have no shared intermediate values. A holder of root cannot calculate the Zcash keys.

The user can set cross-site mode for a site. The wallet uses one key pair for all sites in cross-site mode. Its tag is "cross-site" in place of "site:" + origin.

zafu calculates the key from the origin of the page. In version 1 of the zafu protocol, zafu signs the challenge from the app as raw bytes. zafu does not add the origin to these bytes. The app can put its domain in these bytes. zafu does not read that domain. Thus, zafu does not compare a domain with the host of the page (step 2 of the sequence). zafu shows the origin to the user at the first login to a site. After that login, zafu signs for that site with no prompt for 30 days, while zafu is unlocked. The user can stop this for each site. For a site in cross-site mode, zafu asks the user each time.

If the app puts a nonce and an expiry time in the challenge, the app can refuse an old signature (a replay). A relay is a different attack. In a relay, an attacker gets a real challenge from the app. The attacker sends it to the wallet from a page at a different origin. The wallet signs the challenge with the key of that origin.

  • In site mode, each origin has a different key. Thus, the attacker cannot log in to the account of the user.
  • In cross-site mode, all origins in this mode have the same key. If the user sets this mode for the real app and for the page of the attacker, the attacker can log in as the user.

With steps 1 to 3 of the sequence, the wallet stops a relay: the domain is in the signed message, and the wallet compares it with the page. The zafu sign-in document has this function in the next version: zafu writes the login message itself, with the domain from the origin of the page.

The calculation above is for generation 0 and for the first key of each site. The user can change to a new generation N. Then the name in id is default-vN. The user can also change to a new key N for one site. Then the tag is "site:" + origin + ":" + N. An origin with a port, for example http://localhost:3000, has the tag "site\0" + origin + "\0" + N, where \0 is a zero byte. N is in this tag for the first key too (N = 0). zafu keeps a counter for the generation and a counter for each site. These counters are in the storage of the browser extension, separate from the seed phrase. Thus, after a restore from the seed phrase, the user must also give the counter values to the wallet. The salt and the tags are specific to zafu. A different wallet must use the same calculation and the same counter values to calculate the same keys. An account from a FROST distributed key generation has no seed phrase. Thus, that account has no identity keys. Each participant can log in with the identity keys from the seed phrase of that participant.

Sequence

  1. The app makes a login message, as in ERC-4361. The message has the domain of the app, a nonce and an expiry time. The app makes a new nonce for each login.
  2. The wallet shows the domain to the user. A wallet in the browser also compares the domain with the host of the page.
  3. The wallet signs the message. The secret key is ivk, rsk for the domain, or id_sk for the origin.
  4. The wallet sends the signature to the app. It also sends the address, the key rk, or the key id_pk.
  5. The app examines the signature. It also examines the domain, the nonce and the expiry time. The app accepts each nonce one time only.
  6. If all of them are correct, the user is logged in. The account of the user is the address, the key rk, or the key id_pk.

A wallet on a different device cannot see the page. There, the user must compare the domain in the wallet with the host of the page.

What apps can find from each signature

The app uses a correct viewing key signature as proof that the wallet has the address's ivk. With the memo code, the app checks that the user knows the code only. Each holder of the incoming viewing key can log in as the address. A user who gives the viewing key to a different person also gives the login.

The app uses a correct app key signature as proof that the user has the secret key rsk. Only a holder of ask can calculate rsk. Thus, a viewing key is insufficient for a login.

The app uses a correct identity key signature as proof that the user has the secret key id_sk. A holder of the seed phrase, of root or of id can calculate id_sk. Thus, a holder of a viewing key must also have id_sk for this login.

The app key and the spend key have shared values: rsk = ask + α. The app gets rk and the signature only. The wallet keeps rsk and α with ask. If an attacker gets rsk and α from the wallet, the attacker can calculate ask = rsk − α. The identity keys and the spend keys have only the seed phrase in common. If id_sk is disclosed, ask stays secret.

A FROST group can hold an account, with a threshold of t participants. For that account, t participants make each app key signature together, in a rerandomized FROST round with α. Each participant who has the incoming viewing key can make a viewing key signature alone. Thus, for that account, the threshold is in effect for the app key signature only.

With the app key signature, the app gets rk only. Because α is secret, two apps cannot calculate that their keys are from the same ak. Thus, apps cannot link the app keys of one user.

There, the address of the user stays secret. To show that rk and an address are from the same key, the wallet must also make a zero-knowledge proof. ZIP 304 has this proof for Sapling keys only.

With the identity key signature in site mode, each app gets a different id_pk from a keyed hash. Thus, apps cannot link the identity keys of one user. In cross-site mode, all apps in this mode get one id_pk. Thus, these apps can link the logins of the user. The identity keys have no link to an address. For a login as an address, the app uses the viewing key signature or the memo code.

Parts of a spec

  • Message format. The fields of the login message and their sequence, as in ERC-4361.
  • Receiver. For the viewing key signature. A unified address can have more than one shielded receiver. A Sapling receiver and an Orchard receiver have different ivk values. For each receiver type, all receivers that the wallet gives to senders for one account have one ivk. The change receivers of the account have a different ivk. Developers must give the receiver type in the spec.
  • Calculation of α and of the identity keys. For the app key signature and the identity key signature. One calculation for all wallets. Thus, a user who moves to a different wallet keeps the same accounts. For the identity keys, the zid calculation of zafu is a candidate.
  • Hash personalization. For the app key signature. Wallets already use these keys in transactions. RedPallas has one fixed hash personalization for all signatures. Thus, the wallet signs a hash of the login message, as in ZIP 304. This hash has a personalization for logins only. The wallet calculates this hash itself. The wallet never signs 32 bytes from the app. Thus, a login signature is invalid for a transaction.
  • Transport. A path from the app to the wallet and back. For example, a QR code for the message and an HTTPS request for the signature.
