Basic

Concepts

A shielded payment has a small set of parts: notes, actions, memos, keys and addresses.

Notes

A note contains value. Each note has a recipient, a value and a random seed rseed. A commitment to the note, cmx, is on the chain. The recipient and the value stay secret.

A wallet spends a note with its nullifier. Nodes accept each nullifier one time only. Thus, each note can be spent one time only.

Pools

A pool is a set of notes with one protocol. Two pools are important for new apps:

Ironwood
The newest shielded pool. Its protocol is Orchard. Use it for new apps.
Transparent
A public pool. All values and addresses are visible, as in Bitcoin.

Zcash also has two older shielded pools: Sapling and Orchard. Orchard is the first pool of the Orchard protocol.

Actions and bundles

An action contains one spend and one output. A bundle contains the actions of one transaction in one pool. A bundle has two actions or more. The builder adds dummy spends and dummy outputs to fill the actions.

Outsiders see the number of actions. The real spends and outputs stay secret.

Memos

Each output has a memo of 512 bytes. The memo is in the note ciphertext. The recipient can read the memo. The sender can read it with the outgoing viewing key. The format is in ZIP 302. A text memo is UTF-8 text.

A payment to a transparent address has no memo.

Addresses

A wallet sends a note to an address. A unified address (ZIP 316) contains one receiver for each pool that the recipient accepts. The wallet of the sender selects the best receiver.

A wallet can make many addresses from one key. Only the holder of a viewing key can link these addresses. See Address per customer.

Trial decryption

The recipient of each note is secret. Thus, a wallet must try to decrypt each action with its incoming viewing key. This is trial decryption. Each wallet does this work for each action on the chain. See Polite actions.

Payment requests

A payment request is a URI (ZIP 321). The URI contains the address, the amount and the memo. A wallet reads the URI from a link or a QR code. See Payment links.

Demo: build a unified address

A wallet builds a unified address in three steps (ZIP 316):

  1. The wallet puts the receivers in sequence, from the lowest typecode to the highest. Each receiver has a typecode, a length and its data. The padding is last: the prefix of the address and zero bytes, 16 bytes in total.
  2. The wallet mixes all the bytes with F4Jumble. Thus, when one receiver changes, almost all the characters after the prefix change. The prefix stays the same.
  3. The wallet encodes the result as a Bech32m string with the prefix.

Type or paste a Zcash address. The demo decodes it with the zcash_address crate, compiled to WebAssembly. For a unified address, each receiver has its own color. Clear the box of a receiver. The demo then builds the address again with the other receivers.

Caution

The first address is a test address from the Zcash test vectors. Its keys are public. Do not send funds to it.
