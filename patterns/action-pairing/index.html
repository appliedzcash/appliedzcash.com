Pattern

Canonical action pairing

A builder uses a keyed sort to put the spends and the outputs of a bundle in order. The pairs of spends and outputs are the result of the sort. Thus, each build of the same transaction has the same note commitments.

Problem

Each action of an Orchard-protocol bundle contains one spend and one output. The ρ of the output is the nullifier of the spend in the same action. ψ, rcm and the note commitment of the output are calculated from ρ. Thus, the note commitment of an output changes when its pair changes.

A standard builder pairs spends and outputs at random. It also makes new dummy notes on each build. Thus, each output has a different note commitment in two builds of the same transaction.

The same note commitments are necessary on each build in three cases:

  • Rebuild after a reorg. In a chain of bound notes, the cmx of each predecessor is bound in its successor. After a reorg, a transaction can be gone from the chain. After a rebuild with new commitments, each later note with an old cmx is invalid.
  • Several signers. With FROST over a PCZT, each signer must examine the bundle before it signs. To calculate the expected bundle, a signer needs the dummy notes and the pairs of the coordinator.
  • Receipts before mining. An app can tell a user the note commitment of a note before the transaction is mined. That commitment must stay the same after a rebuild.

Mechanism

Inputs

Each party that builds or examines the bundle uses the same inputs:

  • the pairing key k, a 32-byte secret;
  • an app context ctx, for example an epoch number;
  • the real spends, each with its note and its nullifier key;
  • the real outputs, in the order of the caller;
  • the number of actions n;
  • the lead byte of the note plaintext.

Steps

  1. Sort the nullifiers of the m real spends. Calculate the pairing seed: 
    d = BLAKE2b-256("Zcash_PairingSd_",
      k ‖ len(ctx) ‖ ctx ‖ m ‖ nf_1 ‖ … ‖ nf_m)
  2. Use d as the key of a PRF. Each value has a tag byte t and an index i: 
    PRF_d(t, i, c) = BLAKE2b-512("Zcash_PairingPRF", d ‖ t ‖ i ‖ c)
    c is a counter. It increases only when a value is invalid, for example a spending key.
  3. Make n − m dummy spends of value zero. The spending key, ρ and rseed of each dummy spend are calculated from PRF values.
  4. Give each real output an rseed from the PRF. A caller can give its own rseed, for example for a bound note.
  5. Make the dummy outputs of value zero. The recipient and the rseed of each dummy output are calculated from PRF values.
  6. Calculate a keyed sort key for each spend and each output: 
    key_spend = BLAKE2b-256("Zcash_PairingOrd", d ‖ 0x00 ‖ nf)
key_out   = BLAKE2b-256("Zcash_PairingOrd", d ‖ 0x01 ‖ rseed)
  7. Sort the spends and the outputs by their keys. Action a contains spend a and output a.
  8. The ρ of each output is the nullifier of its action. Calculate esk, ψ, rcm and the note commitment (ZIP 212, ZIP 2005).

A value can be invalid, for example an esk of zero. The chance is about 2−254. Then the builder discards the full build. It adds a retry byte to ctx and builds again. Each party that follows this rule gets the same bundle.

Values that stay random

The value commitment trapdoor, the spend authorization randomizer, the proof and some outgoing ciphertexts stay random. Nullifiers and note commitments are independent of these values. Thus, two canonical builds have different transaction IDs. The same notes are spent in both, so only one of them can be mined.

Scope

The pattern is for bundles with enableCrossAddress = 1, in practice Ironwood-pool bundles. For other bundles, the pairs are set by expanded receiver (ZIP 2006).

Cost

  • Chain Zero. A canonical bundle has the same size and the same fee as a standard bundle.
  • Build A small number of BLAKE2b hashes for each action, and one sort.
  • Builders The builder must accept a pairing key and a context. The orchard crate pairs at random. This pattern is implemented in a fork of the crate, and an upstream PR is pending.
  • PCZT The Constructor role makes the canonical build. A signer with k can build the bundle again and compare nf, cmx and epk of each action before it signs.

Limits

  • Privacy. All derived values are calculated from k. Only a holder of k can identify each dummy note. To all other parties, the dummy notes and the order of actions look random. Thus, keep k as secret as a viewing key.
  • Reused seeds. A dummy nullifier is the same when d is the same. The real nullifiers are bound in the seed, so the same notes are spent in two bundles with the same d. Only one of them can be mined. A unique ctx is necessary for a bundle with zero real spends.
  • Rebuild scope. A rebuild has the same commitments only with the same inputs. With a different fee input, d changes, and then all pairs change.

Spec

The full spec is a draft ZIP. It includes the spending key rule for dummy notes, the dummy output memo, the PCZT fields and the rationale. The draft will be published after review.
