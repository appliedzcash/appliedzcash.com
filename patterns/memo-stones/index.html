Pattern · Experimental

Memo stones

An author sends a memo in a shielded payment. A server calculates one hash from all the memos of a period and puts it in a public record. The author keeps a receipt.

With the receipt, anyone can find the memo in the record. The sender stays secret. The text stays secret until the author shows the receipt.

Warning

This pattern is a proposal. It has no deployed service and no review. Use it on Testnet only.

Problem

An app must show in public that it received a message at a time. The sender and the text must stay secret. Examples are a research result of an agent, a sealed bid, and a report from an employee.

Only the recipient of a shielded payment can read its memo. Thus, outsiders cannot see that the app received the memo. A public post shows the text to all persons.

One use is a retrospective grant for proof of agentic work. A lab records a claim of each result of its agents at the time of the work. Later, the lab shows the receipts to a funder as evidence. The transparent chain gives the time of each claim.

When to use this pattern

Use it in these conditions:

  • other parties must see, at a later time, that the service received a text at a time;
  • the text must stay secret until its author shows it;
  • many authors send texts, and one record for each period is sufficient.

A different design is better in these conditions:

  • Only the author and the service use the fact. Then the memo is sufficient, with no record.
  • The text can be public. Then publish the text.
  • One author needs a timestamp and no service. Then the author can write a hash in a bound note.

Mechanism

Author
A person or an agent with a shielded wallet. The author writes the text.
App
A web page. It writes the memo and the payment link. It keeps the receipt in the browser.
Reader
A server with the incoming viewing key of the service. It finds payments and reads memos.
Writer
A server with one transparent key. It sends the record transactions.
Leaf
The hash of one memo. The memo contains a random salt.
Stone
The Merkle root of the leaves of one period. In a record on the chain, it cannot change.
Record
One stone in a transparent OP_RETURN, with a record number and a leaf count.
Receipt
The memo, the record transaction, and the path from the leaf to the stone.
  1. The app writes the memo from a topic, a random salt and the text. It shows a ZIP 321 payment link, and the author pays it from a shielded wallet.
  2. The reader finds the payment and examines the memo and the amount. It gives the leaf to the writer. The writer does not receive the memo.
  3. At the end of each period, the writer calculates the root of the new leaves: the stone. It sends one record transaction with the stone.
  4. The service publishes the leaf list of the record. The list contains hashes only.
  5. The app finds its leaf in the list and completes the receipt. The author gives the receipt to a verifier at a later time.

The service sends no reply payment. The app uses public data only for steps 4 and 5. Thus, the author needs no account at the service.

Record chain

Each record transaction spends one output of the record before it. Nodes accept each spend of an output one time only. Thus, the records are one chain. The writer cannot make a second history, and it cannot remove a record.

Bound notes give the same property in a shielded pool. This pattern uses the transparent pool, so a usual transparent wallet library is sufficient for the writer.

Verified address writes one salted hash in one bound note, for one user. This pattern writes one root for the memos of many authors.

What the receipt shows

  • The stone of the record contains this exact text, with this topic.
  • The service wrote the record, and the record has one place in the record chain.
  • The text existed at the time of the block.

The receipt does not show the name of the author. Each holder of the memo can show the receipt.

The salt has 256 bits. Thus, outsiders cannot find the text of a leaf by guesses.

Keys

The reader has the incoming viewing key only. The writer has one transparent key with funds for the fees only. The spending key of the service stays offline. See Watch-only keys.

A person who breaks into the reader gets the memos, and gets no funds. A person who breaks into the writer gets the fee funds, and gets no memos.

Cost

  • Each memo One usual shielded payment with two actions. With the ZIP 2009 fee rule, the fee for two actions is 2,000 zatoshis.
  • Each record One transparent transaction for all the memos of a period. Its two outputs are 88 bytes. In ZIP 317, that is three logical actions. With the ZIP 2009 fee rule, the fee is 3,000 zatoshis.
  • Wallets A record transaction has no shielded actions. Thus, a record adds no trial decryption to other wallets. See Polite actions.
  • Receipt The memo and one hash of 32 bytes for each level of the tree. A record of 1,000 leaves has 10 levels.
  • Relay The OP_RETURN script of a record is 45 bytes. Nodes relay an OP_RETURN script of 83 bytes or fewer.
  • Wallet support ZIP 321 with memos. The wallet must send the memo bytes unchanged.

Limits

Warning

The reader sees each memo and each salt. The text is secret from outsiders only. For a text that must stay secret from the service, put a hash of the text in the memo.

  • Refusal. The service can ignore a payment. The author then sees that the leaf is absent from the leaf lists. To show the payment to other persons, the author needs a payment disclosure (ZIP 311, draft).
  • Refunds. The sender of a payment is secret. Thus, the service cannot send back a payment with an invalid memo. The app must examine the memo and the amount before it shows the link.
  • Timing. A record a short time after a payment shows a possible link between the two. A longer period with more leaves makes the link weaker.
  • Leaf list. The leaf list is off the chain. If the service holds back a list, the authors cannot complete their receipts. The authors can see the delay.
  • Empty leaves. The writer can put any hash in a record. Thus, the leaf count is the maximum number of real memos.
  • Copies. The reader refuses a leaf that is already in a record. Thus, a copy of a shown memo gives no second leaf.
  • Reorganization. The reader must wait for confirmations before it accepts a payment.
  • Disclosure. A shown receipt stays public. It shows the topic and the text of one leaf.
  • Truth. A receipt shows that the service recorded a text at a time. It does not show that the text is true.
  • Public data. The records show the number of leaves of each period and the time of each record. Thus, outsiders see how much the service is used.
  • Transparent funds. The fee funds of the writer are public, and so is their source. Use funds with no link to other addresses of the service.
  • Chain data. Each record stays on the chain. A longer period makes fewer records.

Spec

The protocol of today is sufficient: the ZIP 302 memo format, ZIP 321 payment links and a transparent OP_RETURN. The formats in this section are the full spec. The test vectors are in demo/src/memo_stones.rs.

Memo

memo = "DO NOT MODIFY:{ms1/" topic "," salt "}" LF text

topic  1 to 32 characters: a to z, 0 to 9 and the hyphen
salt   64 hexadecimal characters in lowercase
LF     one line feed (0x0A)
text   the text of the author, 1 byte or more

The wallet shows the memo before it sends the payment. The first words are an instruction for the author. The header is 118 bytes at most. Thus, the text has 394 bytes at least.

The reader accepts this format only. It refuses a different prefix, a second comma in the braces, and an empty text.

Leaf and root

leaf = BLAKE2b-256("MemoStones__Leaf", memo)
node = BLAKE2b-256("MemoStones__Node", min(a, b) ‖ max(a, b))

The input of the leaf hash is the memo bytes without the zero padding. The 16 characters in quotation marks are the BLAKE2b personalization. The two values are different, so a leaf is never valid as a node.

  1. The writer puts the leaves in sequence, from the smallest value to the largest.
  2. The writer calculates one node from each pair of leaves, from the left. An odd last leaf goes up unchanged.
  3. The writer does step 2 again with the nodes, until one node stays. This node is the root: the stone.

The two inputs of each node are in sequence by value. Thus, a path is a list of hashes only. With one leaf, the root is the leaf.

Record

The record is the data of one OP_RETURN output:

  1. tag MST1 4 bytes
  2. version 1 byte
  3. number 4 bytes
  4. leaves 2 bytes
  5. root 32 bytes

Total: 43 bytes

The version is 1. The record number and the leaf count are big-endian. The first record has the number 0. Each later record has the number of the record before it, plus 1. The time of a record is the time of its block.

A record transaction has transparent inputs and outputs only:

input 0   output 1 of the record transaction before it
output 0  the OP_RETURN with the record, value 0
output 1  the change, to the record address of the service

The writer can add more inputs to pay the fees. The service publishes the transaction ID of record 0. Record 0 has a leaf count of 0 and a root of 32 zero bytes.

Leaf list

The service publishes one file for each record. The file has the record number, the transaction ID, the root and all the leaves. Anyone can calculate the root from the leaves and compare it with the record on the chain.

Receipt

memo  the exact text of the memo
txid  the ID of the record transaction
path  the hashes from the leaf to the root

A verifier examines a receipt in these steps:

  1. The verifier examines the format of the memo.
  2. The verifier calculates the leaf from the memo.
  3. The verifier calculates the root from the leaf and the path.
  4. The verifier gets the record transaction and compares the root with the root in output 0.
  5. The verifier follows input 0 from record to record, back to record 0.
  6. The verifier reads the time of the block of the record transaction.

Demo: research claims

A lab uses agents for research. An agent sends a claim of each result in a memo. The record shows the time of each claim, and the results stay secret. The lab discloses one result later, with its receipt.
