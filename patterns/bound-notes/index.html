Pattern

Bound notes

Zcash keeps money in sealed notes. Each note has a seal that only its contents can make.

A bound note puts an app's data into that seal. If someone changes the data, the seal stops matching. Everyone can see the change.

Each new note also includes the seal of the note before it. To make the new note, the app must use up the old one. Zcash lets a note be used one time only.

So the app's record is a single chain. Each link is sealed, and each link can come only once. Anyone with the data can check the whole chain.

In technical terms, the seal is the note commitment cmx. An app puts a hash of its data in the rseed of a note. ψ and rcm are calculated from rseed (ZIP 212). Thus, cmx is a commitment to the data.

Standard wallets can decrypt a bound note. Anyone with the data can calculate cmx again and compare it with the chain. The pattern is possible with the consensus rules of today.

Problem

Many apps must keep a public record on the chain. Anyone must be able to examine the record. Examples are a name registry, a decision market and a timestamp service.

A memo is a weak place for a record. The memo is in the note ciphertext, outside the note commitment. To read a memo, a verifier needs a viewing key. Compact blocks contain only the first part of each ciphertext.

The note commitment is a strong place for a record. Nodes add each note commitment to the note commitment tree. Nodes accept each nullifier one time only, so each note can be spent one time only. A record in the note commitment has these two properties.

Mechanism

  1. The app selects a binding domain D. D is 16 bytes. D is unique to the app and to the version of its record format.
  2. The app gives each type of record a kind. The kind is one byte.
  3. The app encodes the record as bytes. These bytes are the fields.
  4. The app calculates rseed:
rseed = BLAKE2b-256(D, kind ‖ len(fields) ‖ fields ‖ prev)
  1. kind 1 byte
  2. len(fields) 8 bytes
  3. fields any length
  4. prev 32 bytes

len(fields) is little-endian. prev is the cmx of the predecessor, or 32 zero bytes.

  1. The wallet builds a usual Orchard-protocol output with this rseed. It calculates esk, ψ and rcm from rseed and ρ (ZIP 212, ZIP 2005). ρ is the nullifier of the note that is spent in the same action.

With the length prefix, the encoding is injective. Two different records always have two different hash inputs.

Chains

A chain is a sequence of bound notes. The first note is the genesis note. Each note after it is the successor of the note before it. prev is the cmx of the predecessor. For the genesis note, prev is 32 zero bytes.

The successor must be the output of the action in which its predecessor is spent. Then ρ of the successor is the nullifier of the predecessor. Nodes accept each nullifier one time only. Thus, each tip has one successor at most. The chain is an append-only record.

This weaker rule is not sufficient: the predecessor is spent in the transaction of the successor. With the weaker rule, one transaction can contain two successors of one tip, and the lineage check is successful for both successors.

For Ironwood-pool bundles, the orchard builder pairs spends with outputs at random. A builder for bound notes must put the successor in the action in which the predecessor is spent. Then the cmx of the successor stays the same after a rebuild of the transaction, if the same predecessor is spent in the rebuild. A rebuild can be necessary after a reorg. The cmx of the change note can change. For stable cmx values in all outputs, see Action pairing.

Verification

A verifier knows the recipient address, the value, the lead byte of the note plaintext and the record. The verifier reads nf_old and cmx from the action. Then the verifier:

  1. calculates rseed from the record;
  2. sets ρ = nf_old;
  3. calculates ψ and rcm from rseed and ρ;
  4. calculates the note commitment;
  5. compares its x-coordinate with cmx.

Only public data is necessary for this check. To check lineage, the verifier also needs the nullifier key nk of the account of the chain. With nk, the verifier calculates the nullifier of the predecessor and finds it as nf_old in the action of the successor. An app with a public chain publishes its full viewing key.

The verifier must also find each transaction of the chain in a block, and the transaction of each successor must be after the transaction of its predecessor. "After" is a later block, or a later place in the same block. This order is not a result of lineage alone. The Merkle path of a spent note is checked in the Orchard circuit only if the value of the note is not zero. Thus, a zero-value note that is not in a block can be spent in a transaction. The checks above are successful for a successor of such a note.

Authority

Anyone can send a bound note to a published address. Thus, each app must define which notes are part of its record. This rule is sufficient to select the notes: the app pins a genesis note by its transaction ID and cmx. A note is part of the record only if it is a descendant of that genesis note. The sender of a false note pays a fee, and the record stays the same. The order of the chain is not known from the pin. See Verification.

Privacy

rseed is a function of the record. A person who knows or guesses the record can calculate rseed, and then esk. With esk, that person can decrypt the note and its memo. Thus, a bound note to a published address is public. For a public registry, this is the correct result.

To keep a bound note private, put a secret of 256 bits or more in the fields. Examples are the hash of a secret key and a random blinding value.

Cost

  • Fee In a usual record transaction, the tip and one funding note are spent. The outputs are the new note and a change note. That is two actions. Since block 3,590,000, wallets use the ZIP 2009 fee rule. The fee for two actions is 2,000 zatoshis (0.00002 ZEC).
  • Wallets Each wallet tries to decrypt each action on the chain. Keep the number of records small. See Polite actions.
  • Verifiers One BLAKE2b hash and one Sinsemilla commitment for each note. The demo below does this work in your browser.
  • Builders The transaction builder must accept an rseed from its caller. It must also let the caller put the successor in the action in which the predecessor is spent. The orchard crate samples rseed at random. add_output_with_rseed is in a patch. The patch is pending upstream. In a PCZT (ZIP 374), the usual rseed field is sufficient for a bound output.

Spec

The full spec is a draft ZIP. It includes the binding domain rules, the amendment to ZIP 212, the lineage check and the security analysis. The draft will be published after review.

Demo: a timestamp registry

With the registry, anyone can prove that a document existed at a block height. Each stamp is a zero-value note to the registry address.

The demo uses the orchard crate, compiled to WebAssembly. The registry key is a demo key. The ρ of the first stamp is a demo value. The previous stamp is spent in the action of each next stamp. Thus, the ρ of the next stamp is the nullifier of the previous stamp.
