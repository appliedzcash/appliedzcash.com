Threshold keys

Give each app role one FROST group key. Any t of n members can sign for the role. Nodes see one usual spend signature.

Warning

FROST on the Ironwood pool is unaudited, and ZIP 312 is a draft. Review by a cryptographer is necessary for the nested construction on this page. Use it on Testnet only.

Test coins

You must have test coins (TAZ) to use a wallet on Testnet. To get TAZ, you must have Node.js 24.7 or later. Run this command with an address of your Testnet wallet: 

npx zcash-faucet@1.2.1 utest1your_testnet_address

Your computer calculates a short proof of work. Then the faucet server sends 0.1 TAZ to the address. No account is necessary. The command has a fixed version. Thus, a later release cannot change the code that you run. The options are in the zcash-faucet repository.

Problem

An Orchard-protocol spend has one signature under one key ak. Thus, shared control of a note must be inside the key.

An app often has roles: a treasury, a registry or a guard. One person with one key is a weak point for each role. The person can lose the key, a thief can take it, or the person can be away when the app must sign.

nLockTime is in effect only for transactions with transparent inputs. Thus, for a shielded note, the structure of the signers is the only path to liveness.

Mechanism

1. One group key for each role

  1. The n members of a role make a FROST key over RedPallas (ZIP 312). Use a distributed key generation (DKG). Then each person has only a share of the secret.
  2. The group key is the ak of the role account.
  3. The members agree on a secret sk in private. From sk, each member calculates the nullifier key nk, the quantum spending key qsk and the quantum intermediate key qk. From ak, nk and qk, each member calculates the commit-ivk randomness rivk. These rules are in ZIP 2005 (Usage with FROST). Each member must keep qsk secret and safe from loss, with the same care as the full secret of ak.
  4. To spend, a coordinator makes a PCZT. Each member examines the transaction on its own and calculates the sighash. Each member refuses a signing package with a message that is different from this sighash.
  5. Any t members sign in two rounds. The randomizer α is in the PCZT, so the signature is valid under rk = ak + [α]G.

The coordinator has zero shares. It has ak, nk and qk (ZIP 2005, key storage). Thus, the coordinator can see the notes of the role. The role continues while t members are available. After a share refresh, each member has a new share. The group key stays the same. The members can also remove a member in a refresh.

2. A public tweak for each object

Some apps need one key for each object: each title, each deed, each account. With a public tweak, each object has its own key:

t          = ToScalar(BLAKE2b-512(domain, object id))
object key = A_G + [t]G
  • Anyone can calculate the object key from the group key and the object ID.
  • For a plain group key, the ak of the object is ±(A_G + [t]G), with sign bit 0. In section 3, the object key is the verifying share of the group, and ak is calculated from it.
  • The address of the object is calculated from ak, nk and rivk. rivk is calculated from ak, nk and qk. Thus, the app that registers objects must have nk and qk. The app can see each object.
  • The members stay offline when the app registers a new object.
  • Each object has its own address. Outsiders see unrelated shielded addresses.
  • To sign for an object, the group adds t to its secret. The coordinator adds the public term one time. When the sign bit is 1, the members negate their shares and the coordinator negates the public term. The coordinator also negates each verifying share before it examines the answers.

3. A group inside a 2-of-2 key

Two parties can be necessary for an object: an owner and a group. For example, the owner moves the object, and the group examines each move for the rules of the app. Make a FROST 2-of-2 key. The owner is identifier 1. The group is identifier 2: 

ak = ±([2]A_O − (A_G + [t]G))

The coefficients 2 and −1 are the result of Lagrange interpolation at zero over identifiers 1 and 2. In the Orchard protocol, the sign bit of ak must be 0. When the sign bit is 1, both sides negate their shares. Each object has its own t and its own ak. Thus, the sign bit can be different for each object. The owner and the guard members calculate the sign bit for each object.

The group signs as one participant of the outer round:

  1. Each chosen member sends the hash of its nonce commitments. Then each member shows its commitments.
  2. The outer commitment of the group is the sum of the member commitments.
  3. Each member calculates its answer from the outer round: 
    z_j = d_j + ρ₂·e_j + λ₂·c·(±μ_j·σ_j)
    ρ₂, c and λ₂ are the binding factor, the challenge and the Lagrange coefficient of identifier 2. μj is the Lagrange coefficient of the member in the group. σj is the share of the member.
  4. The coordinator examines each answer against the verifying share of the member. Thus, the coordinator knows the member of a bad answer.
  5. The coordinator adds the answers and the public term λ₂·c·(±t + α). The result is the share of identifier 2.
  6. The owner signs as identifier 1. The spend signature is a usual FROST aggregate.

The owner must prove possession of its share. A dishonest owner can choose A_O from the group key, and then know the full secret of ak. The proof of possession is the defense against this attack.

Each guard member compares each move with the rules of the app. At registration, the app writes each fixed rule into the first bound note of the object. A royalty rate is an example of a fixed rule. Each guard member compares each move with that note on the chain. Later, an auditor can do the same check. For the approval of one move, each member uses its own record (Approval, in Limits).

4. The owner keeps sk

In ZIP 2005, all participants of a FROST key agree on sk. In a 2-of-2 key, each guard member then has qsk. In this design, only the owner has sk and qsk:

  1. The owner makes sk. Then the owner calculates nk, qsk and qk from sk.
  2. The owner gives nk and qk to the app. The guard members receive nk and qk from the app.
  3. Each guard member also receives nk and qk directly from the owner. It compares these values with the values from the app. Then the guard members can see the object and examine each move.
  4. The owner keeps sk, and a backup of sk with its share. In ZIP 2005, a holder must keep sk or be able to calculate it again.
  5. The owner makes the proof of qsk on its own device. Thus, qsk stays with the owner.

For a spend with the Recovery Protocol, a wallet must show a proof of qsk and a signature under ak. Thus, the owner must also have the signature of the group. The 2-of-2 rule stays in effect while discrete logarithms on Pallas stay hard to find. After an attacker can find them, the owner can possibly move the object with qsk only (Quantum, in Limits). With the ZIP 2005 text, each guard member also has qsk. Thus, after that attack, more persons can move the object alone.

This design has two costs. If the owner loses sk, the object is lost after the switch to the Recovery Protocol. Before the switch, the owner and the group can move the object to a new address. Also, the guard members cannot make sure that qk is from a qsk that the owner has.

Caution

This design is different from the text of ZIP 2005. Review by a cryptographer is necessary. The Recovery Protocol in ZIP 2005 is a proposal. Its details are subject to change.

Cost

  • Chain Zero. The spend has one usual RedPallas signature. To outsiders, it looks like a spend with one key.
  • Rounds Two FROST rounds. A nested group adds one hash round before the commitments.
  • Liveness t members must be online for each spend.
  • Keygen One DKG for each role. A new object has a public tweak, with zero keygen.

Limits

  • Audit. FROST on the Ironwood pool is unaudited. ZIP 312 is a draft. The nested construction is from the recipe of the frostito crate, and review is necessary.
  • Trust. A group is one unit of trust. t bad members are a bad role.
  • Refusal. If all members refuse, the object stays frozen. The remedy is outside the chain, for example in law.
  • Coordinator. Each member must examine the request on its own. Each member must also sign the set of commitments that it saw, so that the coordinator shows the same set to each member. The coordinator must send the randomizer, the message and the commitments over a confidential and authenticated channel (ZIP 312).
  • Message. The member software calculates the signature share over the message in the signing package. It compares that message with its own sighash. Do this comparison in the function that signs, before the software calculates the signature share. Software that compares in a different step can examine one value and sign a different value.
  • Approval. With the sighash, a member knows that it has the same transaction as the coordinator. Each member also compares the transaction with a record that the member keeps, for example the proposal that it approved. A member that uses only data from the coordinator can sign a move that is different from the approved move.
  • Nonces. Each spend has its own signing session. Each member makes new nonces in round one of each session. After a member calculates a signature share, it deletes the nonces (RFC 9591). Keep the nonces in memory only. Member software that stores a nonce can restore it and use it two times. After a reload, the members start a new session. Each member uses only the commitments and the signing package of the current session.
  • Backup. Each member must keep a backup of its share. A member that has sk must also keep a backup of sk. A draft format for this backup is in zcash/zips#1432. The draft is for the plain group key of section 1. Also see Backing Up Key Shares in the FROST book. That section is older than ZIP 2005. With ZIP 2005, the backup must contain sk, because qsk is calculated from sk only.
  • Quantum. With the ZIP 2005 rules, each member of a role has qsk. In the design of section 4, only the owner has qsk. An attacker that can find discrete logarithms can possibly steal the funds with qsk only (ZIP 2005). Thus, when a post-quantum pool with threshold signatures is available, move the funds of each role to that pool.

Spec

FROST for spend authorization is specified in ZIP 312. This page is a design note for the tweak and the nested group, for experiments only.

Demo: a deed with a guard group

In a toy registry, each deed has its own key. The owner has one side. A guard group of three members has the other side, and any two of them sign. The demo uses the reddsa crate (RedPallas FROST), compiled to WebAssembly. A trusted dealer makes the demo keys from a random seed. A real group uses a DKG.
